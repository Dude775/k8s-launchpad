Root cause (11-REVIEW.md WR-01, 11-VERIFICATION.md gap):
In kube-prometheus-stack, `kubeStateMetrics.enabled` is ONLY the subchart *condition*
flag. Values passed *to* the bundled kube-state-metrics subchart (including `resources`)
must live under the subchart's dependency key `kube-state-metrics:` (with dashes). As
written today, `kubeStateMetrics.resources` (values-trimmed.yaml lines 26-28) is not
consumed by any template, so the kube-state-metrics pod runs with no requests/limits.

Current state of values-trimmed.yaml (lines 24-28):
  kubeStateMetrics:
    enabled: true
    resources:
      requests: { cpu: 10m, memory: 32Mi }
      limits: { cpu: 50m, memory: 64Mi }

Target state:
  - `kubeStateMetrics:` retains ONLY `enabled: true` (condition flag).
  - A NEW top-level key `kube-state-metrics:` (hyphenated) carries the same `resources:`
    block (requests cpu 10m / memory 32Mi, limits cpu 50m / memory 64Mi).

The three already-working components stay untouched and confirmed applied (484 MiB
measured): grafana 128Mi, prometheus 256Mi, prometheusOperator 100Mi. Adding the
kube-state-metrics 32Mi request brings the total to the ~516Mi the up.sh preflight
comment already assumes (TRIMMED_STACK_REQ_KI = 516 * 1024).

Certified Phase 11 end state (per 11-03-SUMMARY.md): TORN DOWN — observability namespace
NotFound, all 10 monitoring.coreos.com CRDs retained, both v1.1 apps healthy (0 restarts),
make smoke + make smoke-launchpad PASS.

Live environment quirk (docs/known-limitations.md): on this Windows + Docker Desktop +
kind host, `helm --wait` / `kubectl wait` / watch-based waits hang; observability-up.sh
already uses polling `kubectl get` instead. Do NOT reintroduce `--wait`.
</key_facts>
