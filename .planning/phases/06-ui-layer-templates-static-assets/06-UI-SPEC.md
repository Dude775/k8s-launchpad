# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Stack note:** This project is server-rendered Jinja2 (Flask) + vendored htmx 2.0.10 + vendored Pico CSS 2.1.1 — locked, no React/Vue/Vite/npm build step (CLAUDE.md, REQUIREMENTS.md Out of Scope). The `shadcn`/component-library sections of the standard UI-SPEC template do not apply; this contract adapts the same structure to a classless CSS framework + CSS custom-property theming, which is Pico's documented, build-free customization path.

## Spacing Scale

Declared values (must be multiples of 4, matches Pico's own internal spacing rhythm):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon/label gaps inside status cards, badge padding |
| sm | 8px | Compact spacing between nav items, form field internals |
| md | 16px | Default element spacing — card padding, paragraph gaps (Pico default `--pico-spacing`) |
| lg | 24px | Section padding inside `<main>`, spacing between status cards |
| xl | 32px | Layout gaps — sidebar-to-content gutter |
| 2xl | 48px | Major section breaks (e.g. between landing hero and status-cards section) |
| 3xl | 64px | Page-level top/bottom padding on `<main>` |

Exceptions: Sidebar nav links use a 44px minimum touch/click target height (WCAG 2.5.5 / mobile-friendly minimum), even though 44 is not a multiple of 4 — this is the one standard accessibility exception called out in the base contract questions.

## Typography

Pico CSS ships its own base typographic scale (system font, relative `rem` sizing). This contract pins the phase to exactly 4 roles, mapped onto Pico's native heading/body elements — no custom font-size CSS is needed except where noted.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`1rem`, Pico default `<body>`) | 400 (regular) | 1.5 |
| Label | 14px (`0.875rem` — nav links, card meta text, table headers) | 400 (regular) | 1.5 |
| Heading | 20px (`<h2>`/`<h3>` — page titles, card headers, "Dashboard", "Catalog", "Diagnostics", "Activity Feed") | 600 (semibold — override via `app/static/style.css`, Pico default heading weight is 700; pin to 600 for a flatter platform-engineering look) | 1.2 |
| Display | 28px (`<h1>` — landing page hero title only, e.g. "k8s-launchpad") | 600 (semibold) | 1.2 |

Only two weights declared across the phase: 400 (regular, body/label) and 600 (semibold, heading/display). Do not introduce 300/500/700 anywhere in this phase's templates.

## Color

Pico's stock `pico.min.css` default accent is orange-red (`#bd3c13` light / `#f56b3d` dark) — appropriate for Pico's own docs site, not for a platform-engineering IDP. This phase overrides Pico's documented CSS custom properties in a small companion stylesheet (`app/static/style.css`, loaded after `pico.min.css`), which is Pico's sanctioned zero-build customization path (no SASS, no rebuild). This also resolves Research Open Question 1 (active-nav-state visibility).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--pico-background-color` (Pico default: `#ffffff` light / `#13171f` dark — unmodified) | Page background, `<main>` content area |
| Secondary (30%) | `--pico-card-background-color` / sidebar background (Pico default `--pico-card-background-color`, unmodified: `#f6f7f9` light / `#181c25` dark) | Sidebar nav panel, topbar, status `<article>` cards, table row stripes |
| Accent (10%) | `--pico-primary` overridden to `#2563eb` light / `#3b82f6` dark (blue — conventional "platform/infra" accent, distinct from Pico's stock orange) | Reserved for: active nav link (`aria-current="page"` state), primary CTA buttons (`role="button"` links), focus rings/outlines, links inside body text, htmx-loading `aria-busy` spinner color |
| Destructive | `--pico-del-color` overridden to `#dc2626` (red) | Reserved for: deregister/delete actions (Phase 9), any future destructive confirmation button — not used anywhere in Phase 6's own scope (no destructive action exists yet), declared here so Phase 9 inherits a consistent value without re-litigating this contract |

Accent reserved for: active sidebar/topbar nav link state, the landing page's primary CTA (if any is added — Phase 6 has no CTA per Copywriting Contract below, so in practice this renders as zero accent-button usage this phase), inline text links, focus-visible outlines, and the `aria-busy="true"` loading indicator on the status-cards section during the htmx `load` request. Never apply accent color to body text, card borders generally, or decorative elements.

**Degraded/unknown status card color:** Uses Pico's neutral/muted text color (`--pico-muted-color`), NOT the destructive red and NOT the accent blue — a status card showing "unknown" is neither an error nor a call-to-action; it is neutral information. Reserve red exclusively for genuinely failed/down states in later phases (Phase 7+).

## Visual Hierarchy

**Primary focal point (landing page `/`):** the status-cards section. It carries the live platform data (UI-03/UI-04), is the only region that updates via htmx polling, and is what a human reviewer should read first to judge platform health. It sits in the upper content area of `<main>`, directly below the `<h1>` hero title, separated from the hero by the `2xl` (48px) section break so it reads as the dominant content block.

**Secondary:** the sidebar navigation (persistent orientation/wayfinding, accent only on the active link) and the topbar brand label. These frame the page but must not out-weight the status cards visually — sidebar/topbar use the secondary (30%) surface color and never the accent fill.

**Tertiary:** the hero title and any supporting descriptive copy — present for context and IDP framing (UI-01), but deliberately quiet (Display weight 600, no accent) so they orient without competing with the status cards for attention.

Executor rule: when two elements compete for emphasis on the landing page, the status-cards section wins. Do not add accent color, heavier weight, or larger size to sidebar/topbar/hero in a way that would pull the eye away from the status cards.

## Interaction Contract (htmx) — Phase-Specific Addendum

Not in the base template, but required by this phase's success criteria (UI-04) and carried from `06-RESEARCH.md` Pattern 3 as a binding contract, not just a suggestion:

| Property | Value |
|----------|-------|
| Poll target | `#status-cards` section on `/` (landing page only — no other route polls in Phase 6) |
| Poll route | `GET /partials/status-cards` (fragment-only, never a standalone page — see Research Pitfall 3) |
| Poll interval | `every 15s` (satisfies "≥10s" success criterion with headroom) |
| Visibility guard | `[document.visibilityState === 'visible']` bracket filter on the `every 15s` trigger, plus a `visibilitychange[document.visibilityState === 'visible'] from:document` trigger for immediate resume-on-refocus |
| Swap mode | `hx-swap="innerHTML"` |
| First paint | Server-rendered fallback markup ("Loading platform status…") must be present inside `#status-cards` before any JS runs — page must be meaningful with JS/htmx disabled entirely, per progressive-enhancement intent of the locked stack |
| Degraded state | The partial route ALWAYS returns HTTP 200 with the "Status unavailable" empty-state copy in Phase 6 (no data source exists yet) — never 500, never an empty response body |
