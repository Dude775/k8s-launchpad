# Phase 9 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Stack note:** Server-rendered Jinja2 (Flask) + vendored htmx 2.0.10 + vendored Pico CSS 2.1.1 — locked, no React/Vue/Vite/npm build step (CLAUDE.md, REQUIREMENTS.md Out of Scope). shadcn gate is not applicable (confirmed absent again this phase — no `components.json`/`package.json` at repo root; same finding as `06-UI-SPEC.md`). This contract **inherits and does not redeclare** the Phase 6 spacing/typography/color token system in `app/static/style.css` — it only specifies the NEW contracts this phase introduces: forms, tables, event-row anatomy, confirm pages, and empty states, per the `<design_system_state>` scope note from the orchestrator.

## Color

Inherited verbatim from `06-UI-SPEC.md` (60% dominant `--pico-background-color`, 30% secondary `--pico-card-background-color`, 10% accent `--pico-primary` = `#2563eb`/`#3b82f6`, destructive `--pico-del-color` = `#dc2626`). No new hex values introduced.

Accent reserved for (this phase adds to the Phase 6 list — full list, supersedes for this phase's scope):
- Active sidebar/topbar nav link state (Phase 6, unchanged)
- Inline text links (Phase 6, unchanged) — includes catalog table's service-name link and event-row service links
- Focus-visible outlines (Phase 6, unchanged)
- `aria-busy="true"` loading indicator on `/partials/feed` polling (new, same pattern as status-cards)
- **Primary CTA buttons this phase:** "Register Service" (catalog page), "Onboard your first service" (empty state), "Register Service" (form submit button)

Destructive (`--pico-del-color`, `#dc2626`) reserved for (first real usage — Phase 6 declared this token but never used it):
- The "Deregister" link/button on the service detail page
- The confirm-page's final destructive submit button ("Deregister <name>")
- Inline field-level validation error text on the onboard form

**Environment badges** (dev/staging/prod on catalog table + detail page): use the existing **neutral/muted** treatment (`--pico-muted-color` text, `--pico-card-background-color` or transparent background, no border-left health-signal styling) — these are NOT status-card health modifiers (`--ok`/`--degraded`/`--unknown`) and must not reuse that CSS. Environment is metadata, not a health signal; reserving accent/destructive color for it would visually compete with the real health signals on the dashboard. Render as plain inline text in the table (`{{ service.environment }}`) — no badge/pill styling needed for this phase's scope (a colored pill component would be new, undeclared visual weight; defer unless the checker flags scannability as a problem).

**Focal points** (per ui-checker Dimension 2 recommendation — one visual priority per screen):
- `/catalog` — the catalog **table** is the focal point (or the CTA empty-state card when no services exist); the "Register Service" button is the secondary anchor, top-right of the section heading.
- `/catalog/new` — the **form** is the focal point; nothing else competes on the page body.
- `/catalog/<name>` — the **Registration field block** is the focal point; "Related Events" is secondary, below.
- `/catalog/<name>/delete` — the **confirmation heading + destructive button** are the focal point; the page contains nothing else actionable except Cancel.
- `/feed` — the **event-row list** is the focal point; the polling refresh is invisible chrome, never a spinner takeover.

## Form Contract (CAT-02, CAT-03 — new this phase)

Fields, in display order (per D-01, locked):

| Field | Input type | Required | Label | Help text |
|-------|-----------|----------|-------|-----------|
| `name` | `<input type="text">` | Yes | "Service Name" | "Lowercase letters, numbers, and hyphens only. This becomes the service's URL (e.g. /catalog/my-service)." |
| `repo_url` | `<input type="url">` | Yes | "Repository URL" | "The service's Git repository, e.g. https://github.com/org/repo." |
| `owner` | `<input type="text">` | Yes | "Owner" | "Team or person responsible for this service." |
| `description` | `<textarea rows="3">` | No | "Description" | "Optional. A short summary of what this service does." |
| `environment` | `<select>` (dev / staging / prod) | Yes | "Environment" | none needed — options are self-explanatory; default selection is "dev" |

Layout: single-column stacked form (not multi-column) — matches Pico's default form rendering and the platform's existing single-column content rhythm; no new grid is introduced. `md` (16px) vertical gap between fields.

Label placement: `<label>` above its `<input>` (Pico default block-label behavior) — do not use inline/floating labels (not a Pico pattern, would require new CSS this phase doesn't need).

Validation error placement: inline, directly below the offending `<input>`, inside the same `<label>` block, styled with the destructive color token (`--pico-del-color`) at Label size (14px/400). On re-render after a failed submit, all field errors show simultaneously (not one-at-a-time) and all previously entered values are preserved in their inputs (per D-06, locked) — except the CSRF token, which is always freshly issued.

Accessibility note (explicit, per ui-checker recommendation): rendering the error text inside the same `<label>` block provides implicit label/error association via Pico's native label-wrapping — screen readers announce the error along with the field label. This satisfies the error-association requirement; no `aria-describedby` wiring is needed.

Focus handling after validation failure: the first field with an error receives focus on page load (`autofocus` attribute on that field's `<input>`, computed server-side by the template — not JS) so keyboard/screen-reader users land directly on the first problem instead of the top of the page.

Button hierarchy: "Register Service" (accent-filled, `role="button"`, Pico default primary button styling — no new class) is the only primary action; "Cancel" is a plain text link (Pico default `<a>` styling, no button role) positioned after the submit button, not before — submit is the expected default action a user tabs/clicks to first.

## Table Contract (CAT-01 — catalog list, D-07 locked)

Columns, in order: Name (link to `/catalog/<name>`) → Environment → Owner → Registered At.

| Column | Format |
|--------|--------|
| Name | Plain text link, accent color via Pico's default `<a>` styling inside `<td>` — no button styling, this is navigation not action |
| Environment | Plain text, muted color (see Color section above) — no badge/pill |
| Owner | Plain text, Body size |
| Registered At | Relative-or-absolute: render as absolute date in `YYYY-MM-DD` format (e.g. `2026-07-12`) — matches the kubectl-style precision already established on `/diagnostics` tables (Age column uses concrete units); do NOT introduce a relative-time library or JS for this column — keep it a pure server-side `strftime` |

Sort order: newest-registered first (descending by `registered_at`) — gives the demo-relevant "what did I just add" service visibility at the top, consistent with the feed's newest-first convention (D-11).

Table styling: bare Pico `<table>` element, identical markup pattern to `partials/cluster_state.html`'s pods/deployments tables (`<thead><tr><th scope="col">`) — no new CSS class, no zebra-striping override (Pico's default card-background alternation, already active, is sufficient).

## Event-Row Anatomy (FEED-01/02, D-09, D-11 — shared partial for /feed and detail page)

One partial template renders each event row; consumed by both `/partials/feed` (list of all events) and the detail page's "Related Events" section (filtered to one service). Structure, left to right:

| Element | Content | Notes |
|---------|---------|-------|
| Icon glyph | Text-only Unicode glyph per event type (no icon font/SVG, per Icon library: none) — `●` for `platform_started`, `+` for `service_registered`, `−` for `service_deregistered` | `xs` (4px) gap to the text that follows; glyph color: accent for `service_registered`, destructive for `service_deregistered`, muted for `platform_started` — mirrors the health-signal color discipline already established for status cards (never introduce a new color for this) |
| Event type | Human-readable label: "Platform started" / "Service registered" / "Service deregistered" | Body size, weight 400 |
| Service name | The affected service's `name`, rendered as a link to `/catalog/<name>` when the event has a `service_name` (registered/deregistered events); omitted entirely for `platform_started` (no service attached) | Accent link color, same as table Name column |
| Relative time | e.g. "2 minutes ago", "3 hours ago" | Label size (14px/400), muted color — server-computed relative string (Python, not JS) so it renders correctly on first paint before any htmx swap; recomputed fresh on every poll/full-render since it's server-side |

Row layout: single line where content fits (flex row, `xs` gap between icon and type, `sm` gap between type and service name, relative time right-aligned or trailing) — wraps naturally on narrow viewports, no fixed-width columns (this is a list of rows, not a table, since events don't share the tabular structure of the catalog).

List container: newest-first (per D-11), no pagination in this phase's scope (7-day TTL bounds growth per D-10/FEED-03) — if the list is empty, render the Feed empty state (see Copywriting Contract) instead of an empty `<ul>`.

## Confirm-Page Contract (CAT-05, D-08 — server-rendered, zero JS)

Route: `GET /catalog/<name>/delete` renders a standalone page (extends `base.html`, full nav/shell intact — this is a real page, not a modal or fragment).

Layout, top to bottom:
1. Heading (20px/600): "Deregister {{ service.name }}?"
2. Body text (16px/400): "This cannot be undone. The service and its registration will be permanently removed from the catalog."
3. Button row (`lg` / 24px gap above): destructive submit button ("Deregister", `--pico-del-color` filled via Pico's `role="button"` + a delete-intent class, matching Pico's documented secondary/destructive button pattern) followed by a plain "Cancel" text link back to `/catalog/<name>` — same ordering convention as the form (primary/destructive action first, cancel second)

The submit button posts to `POST /catalog/<name>/delete` with the CSRF token embedded in the form (Flask-WTF, per D-04). No `onclick="confirm(...)"`, no JS of any kind on this page — the page itself IS the confirmation step (per D-08, locked, explicitly to stay browser-automation/screenshot-safe).

## Interaction Contract (htmx) — Phase-Specific Addendum

| Property | Value |
|----------|-------|
| Poll target | `#activity-feed` (or equivalent id) section on `/feed` only — catalog and detail pages do NOT poll (static list, refreshed on navigation only; per requirements, no live-update need on catalog was specified) |
| Poll route | `GET /partials/feed` (fragment-only, mirrors `/partials/status-cards` and `/partials/cluster-state` pattern exactly) |
| Poll interval | `every 15s` (per D-11, locked) |
| Visibility guard | Identical syntax to `diagnostics.html`: `every 15s [document.visibilityState === 'visible'], visibilitychange[document.visibilityState === 'visible'] from:document` |
| Swap mode | `hx-swap="innerHTML"` |
| First paint | Server-rendered fallback ("Loading activity…") present inside the poll target before first `load` trigger fires — same progressive-enhancement discipline as Phase 6 |
| HX-Request branching | `/partials/feed` follows the established fragment-vs-full-page split (`partials/feed_events.html` fragment alone vs. a `feed_full_page.html` wrapper) — same pattern as `partials.py`'s existing two routes; do not add a third branching style |
| Onboard form | Full-page re-render only (per D-06, locked) — explicitly NO htmx on the form submit itself, to avoid the CSRF-token-in-swapped-fragment footgun called out in context |
| Delete confirm/submit | Full-page navigation (standard `<form method="post">`), NOT htmx — per D-08, zero-JS requirement |
